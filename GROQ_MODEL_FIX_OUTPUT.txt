GROQ MODEL FIX — full verification record
======================================================================
Date: 2026-08-21
Root cause: query_router.py's _llm_route was hardcoded to
"llama-3.3-70b-versatile", which Groq removed from its catalog. Every
question that fell through to the LLM fallback (out_of_scope,
needs_clarification, and any question requiring free-text name/metric
extraction like signature_play_type) was returning a routing error in
production.

STEP 2 — Vetting against the router's exact production contract
======================================================================
Same payload shape as query_router.py's _llm_route: no response_format
flag, the real _SYSTEM_PROMPT (all 15 functions + scope statement), and
the same parse (raw.strip().strip("```json").strip("```").strip(), then
json.loads). "Correct" means BOTH valid JSON AND the right classification
key/function -- not just "did it respond."

--- qwen/qwen3.6-27b: DISQUALIFIED (hard contract violation) ---
Every response (even ones that eventually contain correct JSON) is
prefixed with a <think>...</think> reasoning block before the JSON,
e.g.:

  Q: "What's the trade value of Donovan Clingan?"
  raw response: '\n<think>\nThe user is asking about the "trade value"
  of Donovan Clingan.\nLooking at the available functions, none of them
  cover trade value. ... Therefore, this question is out of scope.\nI
  will return `{"out_of_scope": true}`.\n...\n</think>\n\n{"out_of_scope": true}'
  JSON valid: False (JSONDecodeError: Expecting value: line 1 column 1 (char 0))

This is not a rate-limit or sampling artifact -- it reproduced on every
non-rate-limited call. query_router.py's parser has no logic to strip a
<think> block, so every real call to this model would crash with
JSONDecodeError. Not re-tested further; disqualified on this evidence
alone.
